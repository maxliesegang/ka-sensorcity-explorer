# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Vite dev server
npm run build      # tsc typecheck + production build to dist/
npm run preview    # serve the production build
npm run typecheck  # tsc --noEmit
npm test           # vitest run
```

There is no linter configured. `tsc` (strict, with `noUnusedLocals`/`noUnusedParameters`) plus the vitest suite are the correctness gates; `npm run build` runs `tsc` before bundling.

## Architecture

A static SPA reading directly from Karlsruhe's public, read-only ArcGIS REST FeatureServers (the main SensorCity service plus a separate LUBW/HVZ water-level archive), supplemented by DWD weather via Bright Sky — no API key, no backend. The data model is centralized so the UI derives from it.

The three-layer data flow is the key thing to understand:

1. **`src/api/arcgis.ts`** — generic, domain-agnostic FeatureServer client. Knows nothing about SensorCity. Two non-obvious behaviors to respect:
   - ArcGIS returns query errors as **HTTP 200 with an `{ error }` envelope**; `fetchJson` checks for this, so always go through it rather than calling `fetch` directly.
   - `ARCGIS_MAX_PAGE_SIZE` is the hard 2000-row service cap per page. `queryAll` paginates via `exceededTransferLimit` and **requires a stable `orderByFields`** (defaults to `objectid ASC`) for correct paging.
2. **`src/config/layers.ts`** — the entire data model: the 4 FeatureServer layers, plus `CATEGORIES` keyed by the live layer's `beschreibung` field, each mapping to its archive layer id and the measurements to display. The `beschreibung` values are upstream strings that have been renamed before (`Temperatur` → `Temperatur-Sensor`, July 2026) and mismatches fail *silently* — lookups and filters yield empty rather than throwing — so the weather key is exported as `TEMPERATURE_CATEGORY_KEY` rather than repeated as a literal. **This is the primary place to extend the app** (see README's "Extending"); map, legend, detail and query views all read from it. Only stable ids/structure live here — **display labels are NOT stored here**; they live in i18n `common` (see below) and resolve via the `categoryLabelKey` / `measurementLabelKey` / `layerLabelKey` helpers. Adding a category/measurement therefore also needs a matching label entry in both locale `common` files.
3. **`src/api/sensorcity.ts`** — domain access built on the generic client. Normalizes raw features into `Sensor` objects (`toSensor`), fetches per-device history from archive layers, and computes category counts via `outStatistics`. Note `fetchHistory` escapes the device id into a SQL `WHERE` clause.

### History sources (SensorCity vs external)

Not every category has a SensorCity archive layer — `Wasserpegel-Sensor`, for example, is published only on the live layer (no `archiveLayerId`). History fetching is therefore routed through a small provider abstraction rather than calling `fetchHistory` directly:

- **`src/api/history.ts`** — `resolveHistorySource(sensor, category, field)` returns the main SensorCity archive fetcher when the category has an `archiveLayerId`, otherwise falls back to a matching configured provider. This is what the detail view calls.
- **`src/config/historySources.ts`** — declarative map of `(category, field, deviceId) → fallback provider`. Adding a fallback history source for a sensor is a config entry here; adding a provider also requires one typed factory-registry entry in `history.ts` saying how to read it, so a missing implementation is a compile error. `resolveHistorySource` itself stays provider-agnostic.
- **`src/api/hvz.ts`** — paginated reader for the separate LUBW/HVZ water-level FeatureServer. Its `srid` station ids match the main live layer's water-gauge `device_id` values.
- **`src/api/brightsky.ts`** — DWD Rheinstetten (station 04177) hourly/current temperatures via Bright Sky. This is the "undisturbed" out-of-city baseline for the temperature field's deviation mode; it carefully distinguishes genuine observations from forecast-padded hours (`observed` flag).
- **`src/api/temperatureInsights.ts`** — cross-sensor temperature analytics built on the domain client: per-sensor stats, city spread series, and the geolocated frames the temperature field replays. Fetches every temperature sensor's archive with bounded concurrency, which is why that section is opt-in behind `?insights=1`.
  - `fetchCityTemperatureSeries` is the cheap counterpart, and always loads: the same city-wide hourly picture (mean, min–max band, reading count) in **one** request, because the *service* does the aggregation. It rests on `fetchHourlyBuckets` in `sensorcity.ts`, which has ArcGIS group by `CAST(measured_at AS DATE),EXTRACT(HOUR FROM measured_at)` — two SQL expressions that come back **positionally as `EXPR_1` (day epoch) and `EXPR_2` (hour)**, cut in UTC, so the bucket start is their sum. It carries no per-sensor detail, so the two paths are complements, not alternatives. (This is what the upstream ExB dashboard's `∅ Temperatur` view does; there is no dedicated average endpoint.)
  - The demo mirror can't route through `demo/api.ts`'s `/query` interpreter — it doesn't parse those date expressions — so `hourlyBuckets` there bins the snapshot's per-device history directly.

The temperature field view (`/temperature`) draws live sensor readings as Voronoi/Thiessen regions (`src/utils/voronoi.ts`, via `d3-delaunay`), with temperature and baseline-relative ("deviation") display modes and a historical replay. Live temperature colours adapt to the current range; replay temperature colours use a fixed absolute scale for comparison across time. Baseline-station selection logic lives in `src/config/temperatureBaselines.ts`.

### The soil field (`/soil`)

The second field view, over the soil probes, which report one quantity at six stacked bands at once. The map machinery is shared and quantity-agnostic (see below); what is soil-specific is the depth dimension:

- **`src/utils/soilFieldReadings.ts`** — probes as *columns* (`SoilProbeReading.bandValues`, parallel to the profile's `bands`) rather than single readings, plus `getSoilFieldPoints(probes, bandIndex)` for the band on screen and `getSoilBandStats` for the all-bands summary. It also owns the sentinel floor: a probe publishes -328 °C / -5 % on a band it cannot read, and one such value would drag the whole city's scale to an end.
- **`src/utils/soilFieldScale.ts`** — no new ramps. Soil temperature reuses the hue-anchored temperature spectrum, soil moisture the depth-profile heatmap's sequential blue and its diverging dry/wet counterpart. What it adds is the **domain**: one window over *every* band's values, so switching band compares depths instead of re-normalising the picture. Anything drawing a band must keep using that shared scale.
- **`src/api/soilHistory.ts`** / **`src/utils/soilHistoryReference.ts`** — comparison mode loads each probe's last 30 days with bounded concurrency, reduces every depth band to quartiles, and classifies the current reading against that probe's own middle 50%. The DWD Rheinstetten option is deliberately absent because it measures air rather than soil.
- The quantities come from the soil category's `depthProfiles` in `config/layers.ts`, not from a list in the view, so a third banded quantity would appear on its own. The page leads with `SOIL_TEMPERATURE_PROFILE_KEY`; the config order is a data-model concern.

### Map layer (MapLibre GL)

All map views render with **MapLibre GL** over **OpenFreeMap** vector tiles (keyless, no signup — preserving the no-backend/no-API-key design; self-hostable if the public instance is ever unreliable). Three layers own it:

- **`src/hooks/useMapLibreMap.ts`** — create-once/teardown lifecycle. Exposes `{ containerRef, mapRef, isStyleReady }`; **`isStyleReady` is the contract**: sources/layers may only be added after the style loads, so every view's populate effect depends on it and re-runs when it flips. A light/dark theme swap calls `setStyle` (which discards custom layers) and cycles `isStyleReady` false→true, so the same effect re-adds everything. Basemap style per colour scheme lives in `src/config/basemap.ts` (`getBasemapStyleUrl`), resolved via `src/hooks/useResolvedColorScheme.ts`.
- **`src/utils/maplibreGeoJson.ts`** — idempotent GeoJSON helpers (`upsertGeoJsonSource`, `addLayerIfMissing`, feature builders). Geometry is GeoJSON-native **`[lon, lat]`** throughout — `voronoi.ts` emits that order, and feature `id` lives at the top level so `feature-state` can target it.
- **`src/utils/maplibreMarkers.ts`** / **`src/utils/maplibreField.ts`** — presentation. Markers are GPU circle layers whose hover/active ring growth is a data-driven paint expression over `feature-state` (`createInteractiveCirclePaint`), not CSS or DOM. Popups use `buildSensorPopupHtml` (each feature carries its own pre-built popup HTML + tooltip text in its properties, so `bindCircleHoverState`/`bindFeaturePopups` are domain-agnostic; `detailRows` renders a swatched column, e.g. a soil probe's bands, as data so escaping stays in the builder). A field is a `createFieldController` owning three layers — cells (`fill`), markers (`circle`), value labels (`symbol`, native zoom-sizing + collision). The sensor and detail maps add 3D buildings through `addBuildingExtrusionLayer`.

**The field machinery is quantity-agnostic, and must stay that way.** `createFieldController`, `useFieldController`, `boundsFromFieldPoints` and `voronoi.ts` constrain their points to `FieldPoint` (`src/utils/fieldPoint.ts` — lat/lon only); the colour, label and popup for each point are the view's callbacks. `FieldDisplayMode`, `FieldBaselineControls`, `FieldLegend`, `useFieldLabelVisibility` and `useFieldToggle` are likewise shared by the temperature and soil views; `useFieldBaselineSelection` is temperature-specific because soil comparison has no selectable baseline. Cells are a *per-render* option (`showCells` in `FieldRenderOptions`), not a controller one — all three layers always exist, so toggling them never rebuilds the controller — and value labels are drawn either way: centred in the cell when cells are on, below the marker when they're off. `useFieldToggle` takes a storage key, default and URL param key per view (temperature on, soil off for cells) rather than sharing one preference, since the two fields disagree on what the sensible default is. A point's *quantity* field is per view (`temperature` on `TemperatureFieldPoint`, `value` on `SoilFieldPoint`) — don't widen the shared constraint to include one, or a moisture reading ends up typed as a temperature.

**The viewport belongs to the viewer.** A map sets its view *once* and never moves on its own again; every later move is either the viewer's own gesture or a control they pressed. That rule lives in **`src/hooks/useInitialMapView.ts`**, and every map goes through it — `useFieldController` for the field maps, `MapView` and `SensorLocationSection` directly — passing the *context* the view is about: the map itself where there is one view to establish, the sensor id on `/sensor/:id`, which is why navigating to another sensor re-centres and nothing else does. The callback returns `false` for "not yet" (no style, no data) and keeps its one chance open. Nothing else may move the map: not a band or display-mode switch, not a refreshed reading, not a sensor appearing outside the current view, not a language or theme swap (all of which do re-run these effects). The way back is `resetView`, surfaced by `<MapResetViewButton>` — a map that never re-centres itself owes the viewer that button.

Coordinate order is the classic footgun: it is `[lon, lat]` everywhere on the map side, the reverse of Leaflet's old `[lat, lon]`. See `MIGRATION.md` for the full migration record.

Views (`src/views/`) are one-per-route, wired in `src/App.tsx`: Overview (`/`), Sensors (`/sensors`, a searchable table/cards list), Map (`/map`), Temperature field (`/temperature`), Soil field (`/soil`), Sensor detail (`/sensor/:objectId`), Query (`/query`), and About (`/about`, which also hosts the light/dark/system theme switch). Async data fetching goes through the abortable `useAsync` hook (`src/hooks/useAsync.ts`) paired with the `<Status>` component for loading/error/empty states.

**Live data has an age, and the viewer is told it.** `useAsync` returns `loadedAt` and `reload()` alongside the data, and takes `{ reloadOnFocus: true }` — every view drawing live readings passes it, so a tab left open refetches on return rather than presenting the morning's values as current (throttled: data younger than a minute is left alone). Those three are what `<DataFreshness>` renders — "Data from 14:05 · 3 min ago" plus a refresh button — and what `AsyncBoundary` wires into `<ErrorMessage>`'s retry, since an unreliable upstream makes an error an ordinary state. Two rules to keep: a *refresh* holds the current data on screen while it reloads, a *deps change* clears it (different data must never be labelled as the new one); and relative times tick via `useTicker` rather than freezing at whatever the last render said.

**A long wait is counted, not streamed.** The two loads that fan out one archive request per sensor — `fetchTemperatureInsights` and `fetchSoilHistoryReferences` — know their total up front, so `mapWithConcurrency` takes an `onBatchProgress` callback, the loader passed to `useAsync` receives it as its second argument (`(signal, reportProgress) => …`), and `AsyncBoundary` renders KERN's determinate `<KernProgress>` instead of the spinner whenever `state.loadProgress` is set with a total above 1. `loadProgress` never outlives its load: cleared on start and on settle, and reports after abort or terminal resolution/rejection are dropped; fan-out siblings are aborted when the load fails. What does **not** happen is publishing partial results: every figure those two produce is a *cross-sensor comparison* (warmest now, city spread, replay frames), and a "warmest" over the sensors that have answered so far names a different sensor every second — the same reason a deps change clears data rather than relabelling it. What the viewer keeps meanwhile is the data they already had: `/soil`'s comparison mode holds the value colours until the references exist (`isHistoryComparisonActive` requires `historyState.data`), rather than greying every probe to "unavailable" for the length of the fetch.

**Freshness is a filter, not a footnote.** `/sensors` filters on `isRecentlyMeasured` via `?status=reporting|stale` and badges each card with `<SensorFreshnessBadge>`, because "which sensors stopped reporting?" is asked as often as "where is this one?". Its CSV export writes the **whole filtered set**, not the visible page, so a shared filter and its download describe the same sensors. `/query`'s `<FieldPicker>` is the one caller of `fetchLayerFields` — the layer's real columns as toggles into `outFields` (`toggleOutField` keeps `*` and an explicit list from ever coexisting) — and it fetches only once opened, since most visitors already know the column they want.

**The overview answers before it reports.** `getCityConditions` (`src/utils/cityConditions.ts`) derives how warm / how high from the live layer, and every category card is `summarizeCategoryReadings` — the median over everything reporting, with its range and count — because one sensor's reading at headline size reads as a statement about the city. The gauges are the exception to summarizing: `WaterConditions` lists **every** gauge rather than ranking them, because the three sit on the Rhine, the Alb and the Pfinz, and a "highest" names the Rhine every day without saying anything. What each one carries instead is its direction — `getWaterTrend` (`src/utils/waterTrend.ts`) over the HVZ history `fetchWaterTrends` reads through `resolveHistorySource`. Its window ends at the **series' newest reading, not at the clock**: that upstream lags by hours to a day at a time, and a trend measured to now would silently vanish whenever it does, so the period actually covered rides on the result and is shown as the row's tooltip. `<NearMeSensors>` sorts the already-loaded sensors around a browser geolocation fix (`src/utils/geo.ts`); the position never leaves the page. On `/temperature`, `<HeatIslandCallout>` promotes the city-vs-Rheinstetten comparison out of the baseline picker into one button, by calling the model's existing `selectBaseline(DWD_BASELINE_ID)`.


**Charts** — four, and only two of them share a model. `LineChart` and `CityTemperatureChart` are both time × value, so their geometry lives in **`src/utils/chartGeometry.ts`** (pure, DOM-free: `buildTimeValueScale`, `linePath`, `bandPath`, `nearestIndexAtX`) and the chrome drawn from it in **`src/components/chart/ChartChrome.tsx`**; each chart keeps only its own marks. Note `*Scale` elsewhere in `utils/` means a **colour** scale — `TimeValueScale` is the one data→screen mapping, which is why it lives under `chartGeometry` rather than a `chartScale` module. `DepthProfileChart` (categorical bands) and `SensorHistoryAnalysis` (hour slots) deliberately don't use either — they agree with the pair on the outer padding and nothing else. Two contracts to keep: `nearestIndexAtX` binary-searches, so a chart's series must be **chronological** (every archive reader here returns it that way); and `nearestIndexFromPointer` (in `useChartCursor.ts`, the pointer half of that hook's cursor) takes *mark positions in viewBox space*, never data values. All three table-bearing charts share **`ChartDataTable`** — generic over columns, and both memoized *and* deferred until expanded, so hover never re-formats rows and a series of thousands of points costs nothing on load. Pass it `useMemo`-stable `columns`, or the memo is dead weight.

**Current-readings panels (`src/components/readings/`)** — the detail view's "current readings" body is per sensor type, resolved by `getReadingsPanel(category)` (`panel.ts`); the view owns the section chrome and never branches on type. Dispatch is on what a category **declares**, not on its key: `depthProfiles` → `DepthReadings`, everything else → `GenericReadings`. Keep it that way — the profile tab is gated on the same shape, and a key-driven second axis can silently disagree with it (a new banded category would get the tab but flat cards, with nothing throwing). Presentation stays out of `config/layers.ts` (data, no React).

**i18n (`src/i18n/`)** — English/German via react-i18next. Each view has its own namespace (`overview`, `sensors`, `map`, …); shared chrome and domain labels live in `common`. Dictionaries are TS modules under `locales/<lang>/<namespace>.ts`, registered in `resources.ts`. Use `useTranslation("<ns>")` for view text and `useTranslation("common")` for domain labels. **Keep the EN and DE files structurally identical** (the same nested keys — `resources.test.ts` asserts it, since a missing key silently falls back to English); `format.ts` reads the active language from the i18n singleton, so localized formatters re-run when callers subscribe via `useTranslation`.

## Naming rules

These are conventions the codebase already follows; keep new code consistent with them.

- **German stops at the API boundary.** The upstream feed is German (`beschreibung`, `measured_at`, `bodenfeuchte`, `pegel`). German is permitted *only* as opaque wire identifiers — attribute names, `Category.key` values, `Measurement.field` values — and inside `QueryView`'s raw `where`/`outFields` strings, where showing the literal request is the feature. `toSensor()` in `src/api/sensorcity.ts` is the boundary; nothing German crosses it. Domain types, hooks, components and views are English throughout.
  - Consequence: those German field names double as i18n keys (`measurements.luftfeuchte.label`). That is why upstream strings must each have exactly one home in `config/layers.ts` — see `TEMPERATURE_CATEGORY_KEY` / `TEMPERATURE_FIELD_KEY`. A rename upstream fails *silently* (filters yield empty rather than throwing).
- **archive / history / series** are three distinct levels: *archive* = the upstream layer (`archiveLayerId`), *history* = the fetched result (`fetchHistory`, `resolveHistorySource`), *series* = a chart-ready sequence (`spreadSeries`).
- **profile / band / grid** are the depth feature's three levels, mirroring the above: *profile* = the declared family of banded fields (`DepthProfile`, in `config/layers.ts`), *band* = one depth of it, *grid* = the resampled depth × time model a chart draws (`buildDepthProfileGrid`). A measurement a profile covers is *banded*; one no profile covers is *unbanded* (`getUnbandedMeasurements`) — the two partition a category's `measurements` exactly.
  - `DepthBand.band` is an ordinal rank (0 = shallowest), never a distance: the feed publishes stacked bands and no real depths (cm). Don't rename it to `depth`, which would imply one. `band` also stays clear of `index`, which the grid code uses for array positions.
  - A grid `cell` is a value **plus its provenance** (`DepthProfileCell.isInterpolated`): short reporting dropouts are interpolated so the heatmap stays comparable across them, longer outages stay `null`, and the bound between the two is `MAX_INTERPOLATED_COLUMNS`. Anything rendering cells must keep the distinction visible (the chart marks interpolated columns on a rail outside the plot; the readout and data table say it in words) — colouring filled-in cells as measured without saying so claims readings that were never taken.
  - `DepthProfileGrid` always contains absolute archive values. Display modes are derived by `buildDepthProfileView`: absolute passes the grid through, while development centres every band on its own measured median and keeps a symmetric delta range. Keep that transformation out of archive resampling so current values, provenance and future display modes continue to share one source of truth.
- **view / fit / frame** are three different things on a map: *view* is where the map is looking (`resetView`, `useInitialMapView`); *fit* is one way to reach a view (`fitToBounds`), a centre-and-zoom jump another. *frame* is **not** a viewport word — the historical replay owns it for a time-slice of readings (`HistoricalTemperatureFieldFrame`, `frames`, `selectedFrame`).
- **provider / source / kind**: *provider* is the identity of an upstream network (`HistoryProvider`, `TemperatureProvider` — `"sensorcity" | "hvz" | …`); *source* is a descriptor bundle that **has** a provider (`FallbackHistorySource`, `HistorySourceMetadata`); *kind* is reserved for discriminated-union tags (`legend.kind`).
- **reading vs observation**: a *reading* is any sensor value (the user-facing word — `currentReadings`, `LiveTemperatureReading`). *observation* is reserved for `brightsky.ts`, where it carries a real distinction: a genuine DWD measurement as opposed to a forecast-padded hour (`observed`). Don't collapse the two.
- **Verbs**: `query*` = raw ArcGIS `/query` transport (`api/arcgis.ts`) — a domain module wraps it under `fetch*` rather than re-exporting the name (`fetchLayerCount = queryCount`, `fetchArchiveFeatures`); `fetch*` = any domain-level network read; `get*` = pure in-memory lookup (`getCategory`, `getCategoryColor`, `getPrimaryMeasurement`, `getLiveTemperatureReadings`); `build*` = construct a derived model or scale from data (`buildAdaptiveTemperatureScale`, `buildDepthProfileGrid`); `to*` = coerce/normalize one value (`toSensor`, `toFiniteNumber`); `format*` = render for display (`formatValue`, `formatPrimaryReading`). Booleans are predicate-shaped (`is*` / `has*`), except where a name is fixed by something outside the app: wire fields (`exceededTransferLimit`, `returnGeometry`), library props (`NavLink`'s `end`), and `useAsync`'s `loading`.
  - Two deliberate exemptions to the verbs rule: `demo/api.ts` mirrors the surface it stubs, so its exports are named after their real counterparts (`history`, `count`, `layerFields`) rather than verb-prefixed; and pure math/array helpers (`mean`, `nearestPoint`, `observedOnly`) are not lookups and take no `get*`.

## Conventions & gotchas

- **HashRouter + relative `base: "./"`** (vite.config.ts) is deliberate — it keeps the build portable to any `https://<user>.github.io/<repo>/` GitHub Pages path. Don't switch to BrowserRouter or hardcode a base.
- Archive layers are **rolling windows**, so history is inherently limited to what the service currently retains — not a bug. The main archives retain weeks to months; the separate water-level archive currently retains only a few days.
- **The upstream service is not stable and breaks silently.** It has renamed a category (`Temperatur` → `Temperatur-Sensor`), deleted a layer and renumbered the rest, and migrated soil sensors onto depth-banded fields — all without notice, and none of it throws. When something renders empty, check the live feed before the code: `.../FeatureServer?f=json` for layers, and a `groupByFieldsForStatistics=beschreibung` count for category keys. Layers also declare fields they never populate (`pm10`, `pm25`, `windgeschwindigkeit`, UV are all 0 rows), and soil bands 6–7 return sentinels below absolute zero, so a field existing does **not** mean it has data.
- **The live and archive layers do not carry the same columns.** `niederschlag` is on the weather *archive* (layer 2) and not on the live layer at all — a live query naming it returns a 500 rather than nulls. That is why the overview's rain answer is a second request (`fetchCityPrecipitationStatus`) instead of a read of the sensors already loaded, and why a category's `measurements` can list a field the detail view will always show as "—". It is also **a cumulative tip counter, not an amount**: a station holds the same number for weeks and steps up only while it rains, then wraps back to a small value on a device reset. A non-zero reading therefore says nothing about today — the rain answer asks how much each station's counter *rose* inside the window (`src/utils/precipitation.ts`, shared with the demo mirror), which is why that reader pulls the window's rows per station instead of one `max` each. The increments don't behave like the declared millimetres either, so the UI states wet/dry and never quotes an amount.
- After changing `config/layers.ts`, re-run `npm run capture:demo` — the demo snapshot is keyed by layer id, category key and field name, and `src/demo/api.ts` returns `?? []` on a miss, so a stale snapshot blanks demo mode silently rather than erroring.
- Styling uses the **KERN UX** design system via `@kern-ux-annex/kern-react-kit`; MapLibre GL + OpenFreeMap vector tiles for the map. Both CSS bundles are imported in `main.tsx`.
- Deploy is automatic: pushing to `main` triggers `.github/workflows/deploy.yml` → GitHub Pages.
- `karlsruhe_sensorcity_api.md` is the upstream API reference; consult it before changing data access.
